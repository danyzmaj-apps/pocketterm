# Security

## Reporting

Please report vulnerabilities privately through GitHub's private vulnerability reporting: [Report a vulnerability](https://github.com/danyzmaj-apps/pocketterm/security/advisories/new) (the repo's **Security** tab). Don't open a public issue. You'll get an answer within a week, and credit in the advisory if you want it.

## Scope

- The apps: the desktop app for macOS and Windows (`apps/pocketterm-desktop`), iPhone and Android (`apps/pocketterm-mobile`), and the shared code (`packages/pocketterm_core`).
- The PocketTerm server (`packages/pocketterm_server`, protocol: [PROTOCOL.md](packages/pocketterm_server/PROTOCOL.md)), both as the server built into the desktop app (`apps/pocketterm-desktop/lib/hosting`) and as the Docker image with Caddy for a VPS (`apps/pocketterm-server`).
- The publisher's push relay (`apps/pocketterm-relay`; who can see what: [its SECURITY.md](apps/pocketterm-relay/SECURITY.md)).
- The desktop app's local API, the omp extension (`apps/pocketterm-desktop/integrations/omp`) and the Claude Code plugin (`apps/pocketterm-desktop/integrations/claude`).

Out of scope: Tailscale, Apple, Google, Microsoft, Docker, Caddy and Let's Encrypt themselves, and the terminals and coding agents PocketTerm drives; a server whose owner handed its setup link, a pairing code or a computer's QR code to someone else; attacks that need an unlocked device you already control.

Most valuable to hear about: anything that gets a device token without a working setup token or pairing code, gets past the redeem throttle, or uses the server without a device token; anything that reads or changes what a computer seals with its channel key without that key (live messages, images, notifications), or plants a key on a phone; anything that reaches the built-in server from outside the owner's tailnet, or the local API from another user or machine; anything that gets past the relay's checks or limits or makes it send anything but ciphertext or a checked Live Activity state.

What the publisher collects, and what it doesn't: the [privacy policy](https://www.danyzmaj.com/pocketterm/privacy/).

## Model

- **One server per owner.** There is no central PocketTerm server. Each owner runs their own, which serves only their computers and phones. Every device signed in to it belongs to the owner; what keeps one computer's sessions from a device that hasn't scanned that computer's code is the computer's key (below), not the server.
- **Where the server listens.**
  - **On this computer:** the server built into the desktop app listens on 127.0.0.1 only. Tailscale publishes it with `tailscale serve` at `https://<this computer>.<tailnet>.ts.net`, with Tailscale's HTTPS certificate, so only devices on the owner's tailnet reach it. Tailscale Funnel isn't used, so it is never on the internet. The computer itself signs in on 127.0.0.1 with the server's setup token.
  - **On my own server:** `apps/pocketterm-server/docker-compose.yml` runs two containers. Only Caddy is published (ports 80 and 443): it gets the HTTPS certificate from Let's Encrypt and forwards to the server on Docker's network. The server's port (47900) isn't published. The server image holds only the server's executable and the few system files it needs (no shell), and runs as user 65532, not root. The compose file comes from the release tag matching the app (`v<version>`) and pins the server image of that same version.
- **Device tokens.** Every signed-in computer and phone has its own device token: 32 random bytes (43 characters, base64url). The server keeps only its SHA-256. A token works until its device leaves or is revoked, or the server's data is erased; its WebSockets then close (4003). Only computers make pairing codes, revoke other devices and erase the server's data. A computer keeps its token next to its channel keys (below), a phone in the Keychain (iPhone) or app-private storage wrapped by a key in the Android Keystore (Android).
- **Setup link.** A computer signs in with the server's setup link, `pocketterm://setup?url=…&setup=…`. Its setup token is 32 random bytes (43 characters, base64url), reusable by every computer of the owner until the owner makes a new one with `pocketterm-server setup-link --new` (computers already signed in stay signed in). Whoever holds it can sign in a computer: list and revoke devices and erase the server's data, but never read a computer's sessions without that computer's key. The server keeps it in its data folder (the `setup-token` file) so it can print it: anyone who can read that folder can read it.
- **Pairing.** A phone signs in only by scanning a code from a signed-in computer: 28 characters of Crockford base32 (140 bits), of which the server keeps only the SHA-256; single use, valid 10 minutes. An unknown, expired or used code all get the same answer. The two redeem endpoints (setup tokens and pairing codes) share one throttle: after 10 failed redeems from one address within 10 minutes, every redeem from it gets 429 until the oldest failure is 10 minutes old, right code or not. The address is the TCP peer's, and an IPv6 address counts by its /64 (an IPv4-mapped one as the IPv4 address). `X-Forwarded-For` (its last address) counts only with `--trust-proxy` (`POCKETTERM_TRUST_PROXY=1`, which the Docker setup sets because Caddy is the only way in), and on the built-in server only when the peer is loopback (`tailscale serve`). The counters live in memory, so restarting the server clears a lockout; the code space is what makes guessing hopeless. Redeeming gives the phone a device token of its own. Phones never set up servers. The same QR also carries that computer's id and channel key (below), so the QR is a secret: the app says so where it shows it.
- **End-to-end encryption** (`packages/pocketterm_core/lib/e2e.dart`). Each computer makes a 32-byte channel key the first time it needs one and keeps it in the system's secure storage (`apps/pocketterm-desktop/lib/channel_keys.dart`): the login Keychain on a Mac; on Windows, a file in the app's `%APPDATA%` folder encrypted for that Windows user (DPAPI). It never goes to any server: a phone gets it only by scanning that computer's QR code, and keeps it in the Keychain (App Group, this device only, after first unlock) on iPhone, or in app-private storage wrapped by a key in the Android Keystore on Android (excluded from backups and device-to-device transfer), where the push extension (iPhone) or push service (Android) can read it too. Everything between that computer and its phones is sealed with it: AES-256-GCM with a random 12-byte nonce and additional data naming what it is (`pocketterm/v1|<topic>|<event>`, where the topic is the computer's id; `pocketterm/v1|image|<path>`; `pocketterm/v1|push|<desktop id>`; `pocketterm/v1|activity|<desktop id>`), so a message can't be moved to another computer, event, image or push. Every live message carries a timestamp, a random id, its sender's random epoch and a sequence number: the receiver drops one more than 5 minutes off its clock or sent earlier than the receiving app started, an id it has seen in the last 10 minutes, and a sequence number at or below the last one from that epoch. Sealed notifications also carry a timestamp and a random id inside. **Reset key** (computer's Settings → Phone) makes a new key: every phone must scan again, and a lost phone's key stops working. A phone that hasn't scanned a computer's code shows it locked: nothing from it shows and nothing goes to it. Only the in-app scanner adds a key; a link opened from outside the app never does, and one that would sign a signed-out device in to another server waits for the person to confirm.
  - **What your server can see:** your devices' labels and platforms, when each signed in and when it last made a request, your computers' ids, names and platform, the setup token and the SHA-256 of device tokens and pairing codes, your phones' push tokens and Live Activity tokens with the session keys they follow, when and how big each live message is, which computer's topic and which event it is (`state`, `run` …), that an image of some size passed through, iPhone Live Activity states, and callers' addresses (in memory, for the redeem throttle). **What it can't:** your sessions, transcripts, prompts, screens, window titles, folders, images and notification text, all of which it only passes on as ciphertext.
- **Push encryption.** A computer seals each notification (`{title, body, session, state}`) itself with its channel key and hands your server `{desktop, enc, collapse?}`. The server sends the publisher's relay one request per phone, its whole JSON body sealed to the relay's X25519 public key (a fresh ephemeral X25519 key per request, HKDF-SHA256, AES-256-GCM; `packages/pocketterm_server/lib/src/relay.dart`), so nothing between the server and the relay sees the push token, the computer's id or the kind of push. The relay opens it in memory and passes `enc` to APNs (iPhone, opened by the notification service extension) or FCM (Android, a data-only message opened by the app), and stores nothing. A phone without that computer's key shows a generic "PocketTerm" notification with no text. The default relay is `https://push.danyzmaj.com/v1/push`, run by Danijel Lovric on his server in Germany; `PUSH_RELAY_URL` and `PUSH_RELAY_KEY` point a server at another one. Exception: iPhone Live Activity updates stay unencrypted (Apple's servers deliver them straight to the system, which no extension of ours can open) and carry only a coding session's state, a timestamp and, when it needs you, what for (a question, an approval or a plan), never text; the relay rebuilds them from those checked fields only. Android's counterpart is sealed with the computer's key (`pocketterm/v1|activity|<desktop id>`); only its end (`ended` and a timestamp) can go in plain text, when the server ends it itself (its computer quiet for 3 minutes, removed or signed out). The relay's private key, APNs key and Firebase service account are its secrets alone.
- **The relay is open by design.** It can't tell callers apart: self-hosted servers hold no publisher credentials. Anyone who knows a phone's push token can make it show a generic alert (title "PocketTerm", no text), or move or end one of its Live Activities, and nothing more; real text needs the computer's key. Each relay instance limits callers in memory (best effort, gone on restart): 600 requests a minute per caller address (`cf-connecting-ip`, set by the Cloudflare tunnel in front of it), 60 pushes a minute per device token, and a caller with 30 malformed requests or unknown tokens in 10 minutes gets 429 for a while. The counters are keyed by HMAC-SHA256 of the address or token under a random salt that lives only in memory and changes every day.
- **Local API** (`apps/pocketterm-desktop/lib/local_api.dart`). The desktop app's API listens on 127.0.0.1 only, behind a random token in `~/.config/pocketterm/cli.json` (on Windows under `%USERPROFILE%`). On macOS the file is mode 600 and PocketTerm keeps its own `~/.config/pocketterm` folder at mode 700; if that `chmod` fails it writes no token. On Windows the file relies on the user profile's default permissions. omp's extension and the Claude Code plugin use the same token, but only once the app proves it holds it: they ask `/v1/ping` with a fresh nonce, without the token, and expect an HMAC-SHA256 of the port and nonce under the token, so whatever listens on a port a stale `cli.json` names gets neither the token nor any commands. PocketTerm removes the file when it quits. Of the terminals, kitty is reached over its unix sockets in `/tmp`, and only sockets owned by the current user count.
- **Terminal from the phone** (computer's Settings → Phone) lets a phone that holds a computer's key (it scanned that computer's code) read that computer's coding sessions (omp, Claude Code) and terminal screens (macOS: kitty, tmux, WezTerm, Ghostty; Windows: WezTerm), prompt them, answer their questions and approvals, type into the terminal windows, and open or close windows. Each computer uses its own topic on the server's live channel (its 8-character id); the server passes every payload on untouched and stores none of it, and anything that doesn't open with the computer's key is dropped. Images from the phone are sealed with that key, with their path in the additional data, and go to the server sealed as a blob (at most 20 MiB); the server deletes a blob once it has been downloaded in full, and one nobody downloads after an hour.
- **Phone demo mode.** **Try the demo** shows the phone app on a made-up computer answered on the phone itself (`apps/pocketterm-mobile/lib/demo`): no sign-in, no server, no keys, and nothing goes over the network.
- **Updates.** Mac updates are accepted only when signed with the project's Sparkle EdDSA key, and they arrive notarized. The Windows app doesn't update itself: it links to the latest GitHub release, whose installer is not code-signed yet. Phone builds go only to invited testers through TestFlight and Google Play internal testing (Play App Signing). The built-in server updates with the desktop app; a VPS runs the server image its compose file pins until the owner sets another `POCKETTERM_VERSION`.
