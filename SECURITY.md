# Security

## Reporting

Please report vulnerabilities privately through GitHub's private vulnerability reporting: [Report a vulnerability](https://github.com/danyzmaj-apps/pocketterm/security/advisories/new) (the repo's **Security** tab). Don't open a public issue. You'll get an answer within a week, and credit in the advisory if you want it.

## Scope

- The apps: the desktop app for macOS and Windows (`apps/pocketterm-desktop`), iPhone and Android (`apps/pocketterm-mobile`), and the shared code (`packages/pocketterm_core`).
- The backend every user deploys: migrations and row-level security, and the `pair` and `push` edge functions (`apps/pocketterm-desktop/supabase`).
- The publisher's push relay (`apps/pocketterm-desktop/supabase/functions/relay`).
- The desktop app's local API, the omp extension (`apps/pocketterm-desktop/integrations/omp`) and the Claude Code plugin (`apps/pocketterm-desktop/integrations/claude`).

Out of scope: Supabase, GitHub, Apple, Google and Microsoft themselves, and the terminals and coding agents PocketTerm drives; a server whose owner shared their account or allowed someone's sign-up; attacks that need an unlocked device you already control.

Most valuable to hear about: anything that lets one account read or write another's data or join another's terminal topic, reach a computer's terminal bridge or local API from elsewhere, read a push's contents, or get past the relay's checks or limits or make it send anything but ciphertext or a checked Live Activity state.

## Model

- **No shared server.** Each user runs their own Supabase project. Every table has row-level security that limits a user to their own rows, and the apps hold only the publishable key.
- **Private sign-up.** GitHub is the only way in: email and password sign-up is off (`[auth.email] enable_signup = false`, and the setup wizard turns the email provider off), and the `before_user_created` hook also refuses email, phone and anonymous sign-ups (except the demo account below, made by the server). After the first account it lets in only the emails listed in `allowed_signups`.
- **Pairing.** A phone signs in by scanning a one-time code from a computer: 28 random characters, of which the server keeps only the SHA-256; single use, valid 10 minutes. Ten wrong tries from one address in 10 minutes are turned away for a while; the address is `cf-connecting-ip`, which Supabase's Cloudflare edge sets (`x-forwarded-for` and `x-real-ip` are ignored, since a client can write them), so a local stack has no throttle. The code space is what makes guessing hopeless. Redeeming it gives the phone a fresh session of its own. Phones never set up servers and never sign in with GitHub.
- **Reviewer codes.** Made by the owner in the desktop app (**Settings → Reviewer access**) for App Store and Google Play review. Unlike phone codes they are reusable until they expire: 7, 30 or 90 days from the app (the server accepts 1–365). The server keeps only their SHA-256. Each one signs a phone into a separate demo account on the owner's server, which row-level security keeps away from the owner's data. Once none of its codes works, the demo account is shut out: revoking the last working code (or the owner deleting their account) deletes its sessions and refresh tokens at once, and a code running out does the same within 10 minutes (pg_cron); `pair` refuses it with 403 from that moment, and its phone, which asks the server every 30 seconds whether its session still exists, signs out. The access token a phone already holds still passes row-level security on the demo account's own rows until it expires (at most an hour, `jwt_expiry`); it never reaches the owner's. **Delete account** on the demo account empties it (its phones, followed sessions and computers) but keeps the account and the owner's reviewer codes, so codes handed to Apple or Google keep working.
- **Push encryption.** Each phone makes a 32-byte AES key and gives it only to its own server at registration. The server seals every notification with AES-256-GCM (random 12-byte nonce) and sends `base64(nonce ‖ ciphertext ‖ tag)` to the publisher's relay, which passes it to APNs (iPhone, decrypted by the notification service extension) or FCM (Android, a data-only message decrypted by the app). The relay sees the push token, the kind, a collapse id and ciphertext, and stores nothing. Exception: iPhone Live Activity updates can't be encrypted, so they carry only a coding session's state, a timestamp and, when it needs you, what for (a question, an approval or a plan), never text. The relay's APNs key and Firebase service account are its secrets alone.
- **The relay is open by design.** It can't tell callers apart: self-hosted servers hold no publisher credentials. Anyone who knows a phone's push token can make it show a generic alert (title "PocketTerm", text "Terminal"), or move or end one of its Live Activities, and nothing more; real text needs the phone's key. Each relay instance limits callers in memory (best effort): 600 requests a minute per caller address (`cf-connecting-ip`), 60 pushes a minute per device token, and a caller with 30 bad requests or unknown tokens in 10 minutes gets 429 for a while.
- **Local API.** The desktop app's API listens on 127.0.0.1 only, behind a random token in `~/.config/pocketterm/cli.json` (on Windows under `%USERPROFILE%`). On macOS the file is mode 600 and PocketTerm keeps its own `~/.config/pocketterm` folder at mode 700; if that `chmod` fails it writes no token. On Windows the file relies on the user profile's default permissions. omp's extension and the Claude Code plugin use the same token, but only after the server proves it holds it: they ask `/v1/ping` with a fresh nonce, without the token, and expect an HMAC-SHA256 of the port and nonce under the token, so whatever listens on a port a stale `cli.json` names gets neither the token nor any commands. PocketTerm removes the file when it quits. Of the terminals, kitty is reached over its unix sockets in `/tmp`, and only sockets owned by the current user count.
- **Terminal from the phone** lets anyone signed in to the account read each of its computers' coding sessions (omp, Claude Code) and terminal screens (macOS: kitty, tmux, WezTerm, iTerm2, Terminal, Ghostty; Windows: WezTerm), prompt them, answer their questions and approvals, type into the terminal windows, and open or close windows. Each computer uses its own Realtime topic, `terminal:<user id>:<desktop id>`, which only that user can join (RLS on `realtime.messages`); nothing it carries is stored on the server. Images from the phone pass through the private `terminal` bucket, in the user's own folder.
- **Updates.** Mac updates are accepted only when signed with the project's Sparkle EdDSA key, and they arrive notarized. The Windows app doesn't update itself: it links to the latest GitHub release, whose installer is not code-signed yet. Phone builds come from the App Store and Google Play (Play App Signing).
