# Security

## Reporting

Please report vulnerabilities privately through GitHub's private vulnerability reporting: [Report a vulnerability](https://github.com/danyzmaj-apps/pocketterm/security/advisories/new) (the repo's **Security** tab). Don't open a public issue. You'll get an answer within a week, and credit in the advisory if you want it.

## Scope

- The apps: the desktop app for macOS and Windows (`apps/pocketterm-desktop`), iPhone and Android (`apps/pocketterm-mobile`), and the shared code (`packages/pocketterm_core`).
- The backend every user deploys: migrations and row-level security, and the `pair` and `push` edge functions (`apps/pocketterm-desktop/supabase`).
- The publisher's push relay (`apps/pocketterm-relay`; who can see what: [its SECURITY.md](apps/pocketterm-relay/SECURITY.md)).
- The desktop app's local API, the omp extension (`apps/pocketterm-desktop/integrations/omp`) and the Claude Code plugin (`apps/pocketterm-desktop/integrations/claude`).

Out of scope: Supabase, GitHub, Apple, Google and Microsoft themselves, and the terminals and coding agents PocketTerm drives; a server whose owner shared their account or allowed someone's sign-up; attacks that need an unlocked device you already control.

Most valuable to hear about: anything that lets one account read or write another's data or join another's terminal topic, reach a computer's terminal bridge or local API from elsewhere, read a push's contents, or get past the relay's checks or limits or make it send anything but ciphertext or a checked Live Activity state.

## Model

- **No shared server.** Each user runs their own Supabase project. Every table has row-level security that limits a user to their own rows, and the apps hold only the publishable key.
- **Private sign-up.** GitHub is the only way in: email and password sign-up is off (`[auth.email] enable_signup = false`, and the setup wizard turns the email provider off), and the `before_user_created` hook also refuses email, phone and anonymous sign-ups (except the demo account below, made by the server). After the first account it lets in only the emails listed in `allowed_signups`.
- **Pairing.** A phone signs in by scanning a one-time code from a computer: 28 random characters, of which the server keeps only the SHA-256; single use, valid 10 minutes. Ten wrong tries from one address in 10 minutes are turned away for a while; the address is `cf-connecting-ip`, which Supabase's Cloudflare edge sets (`x-forwarded-for` and `x-real-ip` are ignored, since a client can write them), so a local stack has no throttle. The code space is what makes guessing hopeless. Redeeming it gives the phone a fresh session of its own. Phones never set up servers and never sign in with GitHub. The same QR also carries that computer's channel key (below), so the QR is a secret: the app says so where it shows it.
- **End-to-end encryption.** Each computer makes a 32-byte channel key the first time it needs one and keeps it in the system's secure storage (the login Keychain on a Mac, Credential Manager on Windows). It never goes to any server: a phone gets it only by scanning that computer's QR code, and keeps it in the Keychain (App Group, this device only, after first unlock) on iPhone or Keystore-backed storage on Android, where the push extension can read it too. Everything between that computer and its phones is sealed with it, AES-256-GCM with a random 12-byte nonce and additional data naming what it is (`pocketterm/v1|<topic>|<event>`, `pocketterm/v1|image|<path>`, `pocketterm/v1|push|<desktop id>`), so a message can't be moved to another computer, event, image or push. Every live message carries a timestamp and is dropped more than 5 minutes off; each phone message also carries a random id the computer drops when it has seen it in the last 10 minutes. **Reset key** (computer's Settings → Phone) makes a new key: every phone must scan again, and a lost phone's key stops working. A phone that hasn't scanned a computer's code shows it locked: nothing from it shows and nothing goes to it. Links opened from outside the app can add a key for a computer the phone has none for, but never replace one; only the in-app scanner does.
  - **What your server (and Supabase) can see:** who you are, your computers' ids, names and platform, when each was last seen, which phones are registered for push and their push tokens, when and how big each live message is and which event it is (`state`, `run` …), that an image of some size passed through, and Live Activity states. **What it can't:** your sessions, transcripts, prompts, screens, window titles, folders, images and notification text, all of which it only relays as ciphertext.
- **Push encryption.** A computer seals each notification (`{title, body, session, state}`) itself with its channel key and hands your server `{desktop, enc, collapse?}`; the server passes `enc` and the computer's id to the publisher's relay unread, which passes them to APNs (iPhone, opened by the notification service extension) or FCM (Android, a data-only message opened by the app). A phone without that computer's key shows a generic "PocketTerm" notification with no text. The relay sees the push token, the kind, the computer's id, a collapse id (the session's key) and ciphertext, and stores nothing. Exception: Live Activity updates (iPhone) and their Android counterparts stay unencrypted (Apple's servers deliver iPhone ones straight to the system, which no extension of ours can open) and carry only a coding session's state, a timestamp and, when it needs you, what for (a question, an approval or a plan), never text. The relay's APNs key and Firebase service account are its secrets alone.
- **Reviewer codes.** Made by the owner in the desktop app (**Settings → Reviewer access**, shown after pressing ⌥ Option) for anyone who must try a phone build without the owner's account. Unlike phone codes they are reusable until they expire: 7, 30 or 90 days from the app (the server accepts 1–365). The server keeps only their SHA-256. Each one signs a phone into a separate demo account on the owner's server, which row-level security keeps away from the owner's data. Once none of its codes works, the demo account is shut out: revoking the last working code (or the owner deleting their account) deletes its sessions and refresh tokens at once, and a code running out does the same within 10 minutes (pg_cron); `pair` refuses it with 403 from that moment, and its phone, which asks the server every 30 seconds whether its session still exists, signs out. The access token a phone already holds still passes row-level security on the demo account's own rows until it expires (at most an hour, `jwt_expiry`); it never reaches the owner's. **Delete account** on the demo account empties it (its phones, followed sessions and computers) but keeps the account and the owner's reviewer codes, so codes handed to Apple or Google keep working.
- **The relay is open by design.** It can't tell callers apart: self-hosted servers hold no publisher credentials. Anyone who knows a phone's push token can make it show a generic alert (title "PocketTerm", no text), or move or end one of its Live Activities, and nothing more; real text needs the computer's key. Each relay instance limits callers in memory (best effort): 600 requests a minute per caller address (`cf-connecting-ip`), 60 pushes a minute per device token, and a caller with 30 bad requests or unknown tokens in 10 minutes gets 429 for a while.
- **Local API.** The desktop app's API listens on 127.0.0.1 only, behind a random token in `~/.config/pocketterm/cli.json` (on Windows under `%USERPROFILE%`). On macOS the file is mode 600 and PocketTerm keeps its own `~/.config/pocketterm` folder at mode 700; if that `chmod` fails it writes no token. On Windows the file relies on the user profile's default permissions. omp's extension and the Claude Code plugin use the same token, but only after the server proves it holds it: they ask `/v1/ping` with a fresh nonce, without the token, and expect an HMAC-SHA256 of the port and nonce under the token, so whatever listens on a port a stale `cli.json` names gets neither the token nor any commands. PocketTerm removes the file when it quits. Of the terminals, kitty is reached over its unix sockets in `/tmp`, and only sockets owned by the current user count.
- **Terminal from the phone** lets a phone signed in to the account that holds a computer's key (it scanned that computer's code) read that computer's coding sessions (omp, Claude Code) and terminal screens (macOS: kitty, tmux, WezTerm, Ghostty; Windows: WezTerm), prompt them, answer their questions and approvals, type into the terminal windows, and open or close windows. Each computer uses its own Realtime topic, `terminal:<user id>:<desktop id>`, which only that user can join (RLS on `realtime.messages`); everything on it is sealed with the computer's key, and nothing it carries is stored on the server. Images from the phone are sealed with that key before they pass through the private `terminal` bucket, in the user's own folder, and the computer deletes them once used.
- **Updates.** Mac updates are accepted only when signed with the project's Sparkle EdDSA key, and they arrive notarized. The Windows app doesn't update itself: it links to the latest GitHub release, whose installer is not code-signed yet. Phone builds go only to invited testers through TestFlight and Google Play internal testing (Play App Signing).
